Protocol Basics

  • Serial link
    The serial link is established at 9600 baud, 8 bit, no parity, 2 stop. The serial cable needs to be a null-modem type cable (tx/rx swapped).
  • Flow control
    Flow control is done via a form of software flow control. Unfortunately, this flow control is not XON/XOFF, but instead what appears to be a form of the old HP serial terminal ENQ-ACK flow control.
    The mechanics of the flow control used by the Kenwood cd player is of the form:
    • When an event or request needs to be communicated, the initiator of the event/request send the ascii ENQ (0x05) byte
    • Upon receipt of an ENQ, the reciever acknowledges that it is ready to process the event/request with the ascii ACK (0x06) byte
    • Upon receipt of the ACK, the initiator may begin transmitting the event/request.
    • Upon termination of the event/request, an ascii EOT (0x04) byte is sent. The receipt of this final is acknowledged with an ascii ACK (0x06) byte.
  • Event/Request Framing
    The start of an event or request is signaled with the ascii STX (0x02) byte. A command byte is sent along with a payload of the event/request. The receiver of the command signals successful receipt with an ascii ACK (0x06) byte. Unsuccessful receipt is signaled with the ascii NAK (0x15) byte.
  • Payload
    The payload format is of the form:

    2 bytes

    n bytes

    1 byte

    data length (n) (in LSB order)

    data

    checksum
  • Checksum
    A checksum is computed for each payload. This is used to (potentially) detect transmission errors. There does not seem to be any error recovery associated with this checksum. The checksum is computed by: summing the bytes of the command, data length, and data; subtracting 1; and inverting the bits of resulting sum.
  • Reply Framing
    Requests may have reply data associated with them. The format of reply data is virtually identical to that of an event/request frame. The ascii STX (0x02) byte is sent followed by a payload.
